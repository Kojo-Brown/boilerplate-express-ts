# Factory + Registry: `ProviderRegistry`

`src/lib/provider-registry.ts` is the one place this codebase swaps
interchangeable implementations behind a key. The upload feature uses it to
choose a storage backend; the pattern is generic and unaware of storage.

## The problem it solves

Before this, `upload.controller.ts` imported `generatePresignedPutUrl` and
`uploadToS3` directly. That is fine until there is a second backend: the
alternatives then get selected with an `if` in the controller, every call site
has to know which branch it is on, and running the API locally means having AWS
credentials or mocking the module in every test that touches an upload.

A registry moves the choice to one table and leaves every call site identical.

## Shape

```ts
const registry = createProviderRegistry<StorageDriver, StorageProvider>('storage', {
  s3: createS3StorageProvider,
  memory: () => createMemoryStorageProvider(),
});

registry.resolve('s3'); // StorageProvider
```

Three properties are worth the indirection:

**Compile-time exhaustiveness.** `TKey` is pinned to `StorageDriver` rather than
inferred from the table, so the table is checked in both directions against
`Record<StorageDriver, ProviderFactory<StorageProvider>>`:

| Change | What `tsc` says |
| --- | --- |
| Add `'gcs'` to `STORAGE_DRIVERS`, register nothing | `TS2345: … is not assignable to parameter of type 'Readonly<Record<"s3" \| "memory" \| "gcs", …>>'` at the registration site |
| Register `gcs:` without adding it to `STORAGE_DRIVERS` | `TS2353: Object literal may only specify known properties, and 'gcs' does not exist in type …` |

Both errors land in `src/upload/storage/index.ts` — the file that can actually
fix them — not at some downstream `resolve()` that happened to pass the new key.

Inference is still available (`createProviderRegistry('x', { … })` without type
arguments) and is the right call when the table *is* the definition of the key
set. It gives up the check: an unregistered key is simply not part of the
inferred union, so nothing can ever be missing from it.

**Lazy, memoised instantiation.** Factories run on first `resolve`, once. A
deployment running `STORAGE_DRIVER=memory` never constructs an `S3Client` and
never needs AWS credentials to exist. `reset()` drops the memoised instances for
tests that need a provider rebuilt against changed configuration.

**A guarded edge.** `resolve` takes the union. For keys that arrive as strings —
a column, a header, a feature flag — `has()` is a type predicate that narrows
once, and `resolveUnknown()` throws `UnknownProviderError` (a 500 `AppError`,
because a key that does not resolve means the deployment is misconfigured, not
that the caller sent something bad).

## The storage providers

`StorageProvider` (`src/upload/storage/storage.types.ts`) is the whole contract:
`presignPut`, `put`, `publicUrl`. No bucket, no region, no SDK types.

- **`s3`** — adapts the existing `s3.service`. The AWS specifics stay there; the
  adapter is only the shape change, so there is no second copy of anything to
  drift.
- **`memory`** — keeps objects in a `Map` for the life of the process. For tests
  and for running the API without AWS credentials; not durable, not shared
  between processes, not a production option. It implements the real contract
  rather than faking it: keys are generated by the same `buildObjectKey`,
  presigned URLs genuinely expire and are genuinely single-use, and its clock is
  injected so the expiry tests do not sleep.

Both are selected by `STORAGE_DRIVER`, which Zod validates against the same
`STORAGE_DRIVERS` const the registry is keyed by — so an unregistered driver is
rejected at boot with the valid values listed, not on the first upload.

## Adding a backend

1. Add the key to `STORAGE_DRIVERS` in `storage.types.ts`. The build breaks.
2. Write the adapter as a `createXStorageProvider(): StorageProvider`.
3. Register it in `src/upload/storage/index.ts`. The build passes.

Nothing in `upload.controller.ts`, the routes, or the response shapes changes.
